# Data audit: Seattle Building Permits (`76t5-zqzr`)

All numbers below come from the extract downloaded on **2026-10-13 02:41 UTC** (portal refresh
`rowsUpdatedAt` = 2026-10-12 13:29 UTC) and are regenerated by `python -m huskyquiet audit`
into `reports/data_audit_stats.{json,md}`. Re-running the pipeline on a newer extract will
change the numbers slightly; the qualitative conclusions should be re-checked when it does.

**Pagination.** `$order=:id`, `$limit=50000`, `$offset`. SoQL rejects listing individual
system fields next to `*` (`$select=:id,:updated_at,*` returns HTTP 400), so the
ingester uses `$select=:*,*`. Because the dataset is reloaded daily, the ingester
compares `rowsUpdatedAt` before and after paging and retries if the dataset changed mid-download.

## 3. Coverage and quality

* **Historical coverage.** Application dates run from 1990 to 2026-10-10, but records are
  sparse before 2005 (fewer than 400 per year), which points to a system migration around 2005.
  From 2006 on there are roughly 5,000–8,600 applications per year. Modeling forecast dates start
  in 2008, so the 730-day risk set is fully populated.
* **Sentinel dates.** 25 `applieddate` values, 5 `issueddate` values, and 2 `completeddate`
  values are earlier than 1990 (the applied and issued sentinels are `1900-01-01`). They are
  nulled. The 25 applied-date sentinels are a subset of the 46,058 missing application dates
  below, not an extra exclusion. The issued and completed sentinels do not, by themselves,
  remove a record from the model.
* **Inconsistent timelines.** 14 permits have `issueddate < applieddate` (all from 2003–2006).
  They are flagged and excluded from modeling. All 14 still have an application date, so this
  set does not overlap the missing-application-date set or the 25 nulled sentinels.
* **Missing application date.** 46,058 records (23.8%) have no `applieddate` after sentinel
  nulling. They are concentrated in:
  * `EX` exemption requests (100% missing; also never have an `issueddate`), and
  * `RR` roof permits (96% missing, though almost all have an `issueddate`), and
  * `CN` records in intake-stage or closed-out statuses (`Additional Info Requested`, `Closed`,
    `Withdrawn`, `Ready for Intake`, …).

  A record with no application date never entered the review queue in this dataset and
  cannot be placed in a historical risk set, so it is excluded. The two exclusion sets are
  disjoint: 46,058 + 14 = 46,072, and 193,610 − 46,072 = **147,538 model-eligible records.**
* **Coordinates.** 0.6% are missing. All present coordinates fall inside the Seattle bounding box.
* **Cost.** `estprojectcost` is missing for 18% of records, but for 0% of applications since
  2019 (it became mandatory). There are 2,996 zero values. The maximum is $25B, a clear data-entry
  outlier, so the feature is log-transformed and clipped at $5B.
* **City field.** Inconsistent casing (`SEATTLE`, `Seattle`, `seattle`); normalized to upper case.

### Never-issued applications by application year

The share of eligible applications that were never issued rises from about 2.4% (2010–2015) to
about 9% (2022–2024). The 2025–2026 cohorts are higher still because many are still pending. Part of the
older-cohort gap may be **survivorship**: withdrawn or cancelled applications may have been
purged or lost their `applieddate` over time. This cannot be verified from a single
snapshot, which is one reason the model is calibrated on the most recent labelled
period (see `modeling_methodology.md`).

## 4. Leakage audit: what was knowable at a historical forecast date?

The dataset is a **current-state snapshot**. It has no change history, so every field
holds its present-day value. A field is only usable if its value is plausibly fixed at
application time. The diagnostic below compares field missingness for applications
(applied 2010–2024) that were eventually issued with those never issued. A field that is
nearly always empty for never-issued applications is evidently populated during or after
review or issuance.

| Field | Missing, never issued (n=5,114) | Missing, issued (n=100,055) | Verdict |
|---|---|---|---|
| `estprojectcost` | 4.9% | 7.5% | usable (caveat: may be revised in review) |
| `housingunitsadded` | 42.9% | 40.5% | **excluded**: filled in during review (see the recent-cohort check below) |
| `relatedmup` | 86.0% | 91.6% | usable (MUP precedes building permit) |
| `latitude` | 0.4% | 0.1% | usable |
| `permittypedesc` | 3.1% | 1.5% | usable (missing kept as its own category) |
| `contractorcompanyname` | 89.6% | 82.2% | **excluded**: typically recorded at issuance |
| `parentpermitnum` | 99.9% | 93.3% | **excluded**: links created around issuance |
| `zoning`, `dwellingunittype`, `standardplan`, `development_site` | 99.9% | 77–79% | **excluded**: populated at issuance, and only for recent records |
| `readytoissuedate` | 91.6% | 56.2% | **excluded**: a milestone on the path to issuance |
| `totaldaysplanreview` (and the other review metrics) | 89.3% | 73.0% | **excluded**: cumulative values as of today |
| `dependentbuilding = 1` | 0.04% | 2.3% | **excluded** |

**The eventual-issuance comparison is too coarse on its own.** It compares records long after the
fact, by which time most never-issued applications have been closed out. A field that is
filled in *during* plan review looks complete for both groups. A sharper check
(`recent_cohort_pending_vs_issued` in `reports/data_audit_stats.md`) compares applications
from the last 15 months that are **still pending** with those **already issued**. For
`housingunits`, `housingunitsadded` and `housingunitsremoved`, it shows clear
outcome-dependent missingness:

| New-construction applications, last 15 months | Pending: `housingunitsadded` null | Issued: `housingunitsadded` null |
|---|---|---|
| Single Family/Duplex (n = 780 / 943) | 49.7% | 9.3% |
| Multifamily (n = 123 / 24) | 42.3% | 0.0% |
| Commercial (n = 13 / 9) | 53.8% | 22.2% |

The pattern is the same at the class level across all permit types (Single Family/Duplex 49.6% vs 33.6%;
Multifamily 42.0% vs 24.2%). Unit counts are evidently entered or confirmed during review.
A historical snapshot would therefore see a value that, at the time, was often still blank,
so all three housing-unit fields are **excluded**. The same check finds no comparable gap
for `estprojectcost` (0% null in both groups), `relatedmup`, `permittypedesc`, or the
location fields. Pending applications do have higher median costs and more
new-construction keywords, which is consistent with genuine scope differences (bigger
projects take longer) rather than leakage.

**`housingcategory` is assigned at issuance.** The categories "Middle Housing" (14,920),
"Large Multifamily" (1,258), "Multifamily – Other" (450) and "Pre-Approved DADU Plans" (300)
contain **zero** never-issued applications. It is excluded.

**`description` is edited after intake.** City staff append dated administrative
notes, for example `"1/10/17 MD.CANCELLED IAW SBC 106.6.9. …"` and `"4/10/17 HUD. EXTENSION GRANTED …"`:

| Pattern in description | Never issued | Issued |
|---|---|---|
| `CANCEL` | 18.1% | 0.3% |
| embedded date `m/d/yy` | 17.8% | 1.1% |
| `EXPIR` | 0.3% | 3.9% |
| `EXTEN[DS]` | 1.0% | 0.3% |

Raw description text, tokens, and length are therefore **not** used. The text is first
sanitized: every sentence or segment containing an administrative keyword
(cancel/withdraw/expire/extend/void/hold/reissue/IAW/…) or an embedded date is dropped.
Then only a whitelist of 15 project-scope keyword flags is computed (new construction,
demolition, ADU, townhouse, multifamily, tenant improvement, STFI, change of use,
establish use, earthwork, seismic, solar, deck/porch, basement, addition). This is
covered by unit tests (`tests/test_text.py`). A post-hoc ablation measures how much the model relies on
these flags (see the model report).

**Fields that are never features:** `issueddate` (used only to build labels and to define the
risk set), `expiresdate`, `completeddate`, `statuscurrent`, `daysissuepermitcity`, and every
review metric. `tests/test_schema.py` enforces that none of these reach the feature set.

### Residual leakage risks (documented, not fully removable)

1. `estprojectcost`, `permittypedesc`, and `relatedmup` hold present-day values that
   could have been revised during review. Neither diagnostic shows outcome-dependent
   missingness, but a value could still have changed without becoming null or non-null.
   The `no_cost` ablation in the model report shows how much the model depends on cost.
2. In the recent-cohort check, the `kw_establish_use` flag appears in 41% of pending
   Single Family/Duplex applications vs 20% of issued ones. This may reflect
   genuine scope (use-establishment work is slower), or the phrase may be appended to
   descriptions during review. The flag ranks only 9th in permutation importance
   (AUC drop 0.004), and the `no_description_keywords` ablation costs 0.003 AUC, so the
   exposure is small. It is worth re-checking once description history is available.
3. Description sanitization is pattern-based. An administrative note phrased without any of
   the keywords and without a date could survive. The scope whitelist limits the damage.
4. Record survivorship (see §3) can make historical issuance rates look higher than the
   rates of the true application population.

## 5. Status field

`statuscurrent` holds today's status (Completed 134,505; Expired 13,765; Additional Info
Requested 10,256; Closed 8,967; Issued 8,236; Withdrawn 5,210; Canceled 4,577; …). The
dataset never says when a status changed, so status cannot define who was "active" at a
historical date without leaking the future. The risk set uses only `applieddate`,
`issueddate`, and an age cap instead. A withdrawn application stays in the risk set as a negative until it
reaches the age cap.
